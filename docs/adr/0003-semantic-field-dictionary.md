# ADR 0003: Semantic field dictionary as naming authority

- Status: Accepted
- Date: 2026-08-17
- Decision owners: LiMon adjustment team
- Supersedes: none

## Context

LiMon fields appear in API JSON, database columns, Parquet mappings, calculation
functions, labels, filters, and frontend tables. Repeating names across layers
makes renames risky and lets editability/additivity rules drift.

## Decision

`backend/config/data_dictionary.yaml` is the canonical catalog of semantic IDs,
API names, physical names, labels, types, editability, additivity, and stage
dependencies. Backend code resolves names through `FIELDS`. Frontend metadata
is generated by `backend/scripts/generate_frontend_fields.py`.

Generated TypeScript is never edited manually. A physical database rename still
requires a reviewed forward migration and compatibility consideration for
historical JSON snapshots.

## Alternatives considered

- Constants duplicated in Python and TypeScript: rejected because drift is not
  detectable.
- Database column names used everywhere: rejected because transport and user
  labels should not depend on one physical system.
- Runtime schema discovery: rejected because it cannot express business
  semantics such as additivity and calculation dependencies safely.

## Consequences

Field changes begin in YAML and require regeneration. `make check` detects stale
generated metadata. Dictionary validation must reject duplicate or incomplete
entries.

## Verification

Dictionary tests validate uniqueness and derived configuration; frontend build
validates generated types and `make check` regenerates and compares metadata.

## Rollout and recovery

Add compatibility aliases intentionally when historical payloads require them.
Do not use blind repository-wide replacement for a field rename.
